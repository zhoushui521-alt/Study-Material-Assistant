# AI Project Planner

## 目标与边界

把模糊的“想做一个 AI 项目”转化为可验证、可分阶段交付的工程计划：

```text
用户问题 → 产品价值 → 所需能力 → 技术选择 → 阶段拆解 → 验收标准
```

不要从框架、模型或技术名开始，也不要为了展示技术而引入 Agent、RAG、LangChain、LangGraph、Multi-Agent、外部向量数据库或其他基础设施。

本 Skill 只提供规划，不自动授权修改代码、安装依赖、读取秘密、发送用户数据、调用付费服务、迁移数据、提交 Git 或部署。用户同时要求实现时，仍要按仓库规则确认范围、权限和验证方式。

## 先确认规划依据

- 新项目：从用户、场景、痛点、现有替代方案和约束开始。
- 现有项目：先读取适用的项目规则、真实入口、关键调用链、配置、测试、文档和 Git 状态；不要只根据 README、文件名或聊天记录判断能力。
- 把信息标为已验证事实、用户提供、合理推断或待确认，不用假设填补关键事实。
- 缺少的信息不影响方向时，可以给出明确标注的暂定假设；如果会显著改变用户、成本、数据、安全或交付范围，再请求用户决定。

## 规划流程

### 1. 项目定位

先回答“为谁、在什么场景、解决什么问题”：

- 目标用户是谁？
- 任务发生在什么场景和频率下？
- 用户当前怎样完成任务，最痛的环节是什么？
- 问题不解决会造成什么具体损失？
- 哪个可观察结果能说明问题得到改善？

用用户结果描述项目，不用技术实现代替项目目标。例如，“帮助学习者从个人资料中找到并理解可靠知识”是目标，“开发 LangGraph Agent”只是候选实现。

### 2. 产品价值与最小闭环

用以下关系说明 AI 介入的必要性：

```text
Before（当前流程与问题）
  ↓
AI Intervention（AI 只介入哪个关键环节）
  ↓
Expected Improvement（可观察、可测量的改善）
```

分别评估效率、质量、成本、体验与风险。不能验证的收益写成假设，不写成既成事实。优先定义一个最小但完整的用户闭环，避免第一阶段同时建设所有能力。

### 3. 从能力选择技术

对每个候选技术建立因果链：

```text
Problem → Required Capability → Technology Choice → Reason → Simpler Alternative
```

至少检查：

- 固定、可预测的步骤优先使用普通函数或确定性 Workflow。
- 只有知识需要从外部资料动态检索并提供依据时，才考虑 RAG。
- 只有执行路径无法预先可靠确定，且确实需要动态规划或工具选择时，才考虑 Agent。
- 多角色并不自动等于 Multi-Agent；单流程、状态机或单 Agent 能解决时，不增加通信和状态复杂度。
- 框架只是实现选择。先证明能力需求，再比较现有方案、最小方案和退出成本。

明确每项选择解决哪一层问题、增加哪些开发与运行成本，以及什么证据会让团队放弃它。

### 4. 设计当前与目标架构

给出最小必要的数据流和组件关系，并区分：

- 当前已实现架构；
- 本轮准备实现的架构；
- 更远期候选，不得画成已完成能力。

对于 RAG，按 `Document → Parser → Cleaner → Chunker → Metadata → Embedding → Vector Store → Retrieval → Context → LLM → Citation` 定位变化。对于 Agent 或 Workflow，说明状态、节点、工具权限、终止条件和失败回退。

同时写清输入输出契约、数据去向、成本来源、安全边界和关键失败路径。

### 5. 拆分 Stage

按依赖关系和风险递进拆成 `Stage 0-N`。不要为了凑路线图固定阶段数量，也不要把未来设想提前塞进当前阶段。

每个 Stage 包含：

```text
Stage X
Goal: 要解决的单一核心问题
User Outcome: 用户可观察到的结果
Scope: 本阶段包含与明确不包含的内容
Technology: 必要的技术变化
Reason: 为什么现在需要，而不是更早或更晚
Dependencies: 前置条件与数据条件
Validation: 测试、评测或实际操作及通过阈值
Stop Condition: 何种失败会暂停、回退或重做设计
```

阶段验收必须与证据层级匹配，分清代码实现、自动化测试、本地运行、真实模型和生产环境。不能用测试替身或一次演示替代真实效果结论。

### 6. 风险与取舍

至少分析：

- 产品风险：问题是否真实、AI 是否必要、用户是否能完成闭环。
- 数据风险：质量、权限、隐私、偏差、版本与可追溯性。
- 技术风险：错误率、幻觉、检索失败、工具失控与依赖故障。
- 成本风险：模型、Embedding、Rerank、存储、延迟和维护成本。
- 复杂度风险：新框架、状态、基础设施和团队认知负担。

每项高风险给出预防措施、验证方法、触发条件和退出方案。若方案过度设计，应直接指出并给出更小替代方案。

## 输出要求

根据任务规模调整篇幅，不输出没有信息的空章节。默认顺序为：

1. 项目定位
2. 用户问题与当前方式
3. 产品价值与成功信号
4. 能力到技术的选择及架构
5. Stage 规划
6. 各阶段验收标准
7. 风险、取舍与非目标
8. 待确认事项与最近一步

结论先行，解释为什么，再给方案。规划中的指标、成本、时间和能力若没有仓库或用户证据，必须标为待验证估计。

## 完成前自检

- 项目目标描述的是用户结果，而不是技术名。
- 每项技术都能对应真实问题，并比较过更简单的方案。
- 每个 Stage 都有边界、可观察结果和可执行的验收标准。
- 没有把计划、Mock、文档声明或自动化测试写成真实模型或生产事实。
- 没有因规划任务擅自实现、调用外部服务或改变 Git 状态。
